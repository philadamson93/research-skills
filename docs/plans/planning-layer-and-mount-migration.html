A planning layer above plan docs

Plans and repos got big enough that the plan doc stopped being the right unit. There are 262 plan docs across the six repos in active use, and each states its own goal, but nothing states which larger effort it serves, which stage it is, or what comes after. So "why are we doing this at all" has no written home, and every session re-derives it from git, badly. The trackers meant to hold that context grew past being readable, and because they are committed files edited inside 127 checkouts, five checkouts of vista-eval alone hold five different versions. The result is the failure that gets felt: decisions re-litigated, context documents lost, and mistakes that are high-level rather than in the code.

What this is for

Two things get fixed. Every piece of work gets a one-page statement of why it exists and which stage it is at, so the big picture survives between sessions and across the ten things running in parallel. And new plans plus their reviews stop entering git, so they stop costing a personal PHI read — the existing 262 stay frozen in git (already reviewed, free where they sit) and get copied to the mount for cross-project context.

The payoff beyond reading time is structural: a path on the shared mount is not per-checkout, so one board and one set of briefs replace the five diverging copies that exist today.

Stage 0 — Fix the mount-delete hook lands first

The part blocking daily work today. The current gate fires whenever a command contains the literal string /mnt plus any destructive verb, ignoring the actual target — so every mkdir <mount>/boards && rm -rf /tmp/scratch nags. Rewrite it target-bound: resolve each destructive path with realpath, then deny the protected bucket roots outright, pass targets inside a named write-zone allowlist, ask only for a mount delete outside the zone. Nags far less and is strictly safer than the string match.

Stage 4 — Copy plans to the mount, author new ones there now safe changed
Reshaped by your feedback: "we don't need to delete, just copy over and save there." So no git rm, no symlink, no 127-checkout script — the one dangerous step is gone, and so are both symlink defects.

Two moves. Copy every repo's existing docs/plans tree to the mount (non-destructive, checksum-verified) so the manager and any session can read across all six projects, and leave the git originals frozen where they are — already reviewed, free where they sit. From now on, new plans, reviews and explainers are authored on the mount path and never enter git, so they never cost a PHI read. On each save the canonical name stays stable and a dated snapshot lands in <stem>/history/ (your "trivial to add version to filename").

The one cost: during the transition plans live in two places — frozen old ones in git docs/plans, live ones on the mount — so Stage 5 teaches the skills both: search the mount for current work, fall back to git for frozen history. Day to day the board and brief are the index, so nobody greps for a plan anyway.

How we know Copy count and checksums match (a mismatch just means re-copy, nothing lost); a new plan's Reference: resolves and its snapshot lands; the git originals are untouched.

Stage 6 — The manager: holds the big picture, advances, reminds — decides nothing you should refined this round
Refined by your constraint: the manager must never decide anything a task raised for you. "Answers trivial questions" is dropped; the big-picture map is now its lead value; question routing is a board-state queue plus push.

One long-running session that supplies the vantage no single-repo session has. Hard rule: once a task judges "this needs Phil," that is authoritative — the manager passes it through untouched. Its value is altitude and hygiene, not authority. Five jobs:

1. Holds the big-picture map (the lead value) — answers "what are the eight things I'm working on and where does each fit" by joining running sessions (transcript mtime, working dir, token spend) × boards × briefs. Each session resolves to a row: this session is on feat/x, item 3 on the vista-eval board, stage 4 of the matched-cohort program, plan at <mount path>. Degrades to session → branch → nearest doc before the layer exists. A session mapping to no program is itself a flagged inconsistency — untracked work.

2. Watches for high-level inconsistencies (read-only) — cross-repo drift, stage-order violations, a board that disagrees with git, two sessions on one behaviour. Surfaces facts, resolves none. Never reads code.

3. Advances mechanical steps — runs on a loop so you don't type /advance. Procedural progress only; stops at the real gates (plan approval, commit, merge, anything irreversible or costly) and never advances past a question a task raised for you.

4. Reminds an agent that drifted from guidance — the cross-session fix for rules that decay mid-session: it nudges the one drifting session back (a message to that session, not a broadcast). This includes nudging an agent about to escalate a trivial question to apply the filter itself — the nudge goes to the agent, the decision stays with the agent.

5. Routes questions to you, answers none — a blocking question is a state, not a feed entry: the session sets its board entry to blocked-on-Phil, and your "for you" list is a filter over those states. It can't scroll away under concurrent pings, survives the manager dying (state lives in the mount files), and clears when answered. Urgent ones also push immediately; an old unanswered one escalates, getting louder not quieter. You answer in the one manager session; it routes the answer back and unblocks. Conflicts are surfaced the same way, never auto-resolved.

Findings are yes-or-no facts; the key one is a board whose stage disagrees with the newest commit on its branch. Checks retire by measured usefulness (~90% over 20 firings), not by one false alarm. It coordinates through the boards, not by polling peers — so it needs Stage 3 and nothing after it.
