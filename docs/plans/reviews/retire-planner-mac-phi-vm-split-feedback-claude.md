# Feedback: Retire the planner-Mac / PHI-VM split as the VISTA default (Fresh Claude Code review)

## Verdict

**Revise.** The compliance direction is coherent and most of the plan's cited grounding facts check out exactly as claimed, but two of its foundational premises are wrong or unsupported (the "two physical clones" claim, and the uncited "Claude Code for Education is high-risk-data compliant" claim), `claude_ops.md`'s own Phase 1 scope misses two more places that assert "no code execution on this machine," and the cross-repo landing mechanics for Phase 5 + rad-eval are never stated. None of this invalidates the plan's direction, but each needs a concrete fix before implementation.

- **Severity: Critical | The "two physical clones" premise is factually wrong — it's a symlink, not a second clone.** The plan's Background section states: *"research-skills is one GitHub repo cloned twice... not a shared symlink: once at `VISTA/code/research-skills`, once at `RadAWS/code/research-skills`... currently identical at `30cf092` (confirmed — same HEAD, same untracked scratch files)."* I verified directly: `RadAWS/code/research-skills` is a **symlink** to `VISTA/code/research-skills` (`ls -la` shows `research-skills -> /Users/philadamson/Documents/Stanford/VISTA/code/research-skills`; `.git/config` inode numbers for both paths are identical — `38851351`; `os.path.realpath()` resolves the RadAWS path to the VISTA path). There is exactly **one** physical `hooks/lib/phi-free-machines.local` on disk. The "same HEAD, same untracked scratch files" the plan cites as confirmation is trivially true because it's the same directory, not evidence of two clones staying in sync. | Why it matters: this single wrong fact cascades into three sections that describe work/verification against a repo topology that doesn't exist. | Evidence: plan lines 37-42 (Background), 88-97 (Phase 2 "edit in BOTH physical clones"), 167-169 and 181-184 (Files to Modify), 238-241 (Verification "two-clones gotcha" grep), 261-264 (Landing & cleanup merge sequence: `git -C RadAWS/code/research-skills pull --ff-only`) | Required fix: correct the Background bullet; collapse Phase 2's "edit in both clones" step to a single edit (there is nothing to forget, because there is nothing to duplicate — this actually *removes* one of the fail-open risks the plan worries about, see Failure Modes below); drop or rewrite the RadAWS `pull --ff-only` step (pulling into a symlinked path just re-runs `git pull` in the same repository); rewrite the Verification section's "two-clones gotcha" check into a one-line confirmation that the shared path is in fact a symlink (and flag what changes if Phil later un-symlinks it into a real clone — the two-edit machinery would then need to come back).

- **Severity: Critical | Phase 1's `claude_ops.md` scope misses two more places that assert "no code execution on this machine."** Phase 1 names five things to rewrite (Environment Constraints, Hard Boundary, Machine-Aware Operating Mode, Plan Document Structure's VM-handoff framing, VM-status-docs framing). ## Failure Modes

- **Scenario: implementer removes the Mac from `phi-free-machines.local` before wiring `phi-vet-gate.sh` into `settings.json`.** Phase 2 bundles both steps but states no required sub-order. Because `phi-vet-gate.sh` is inert while the machine is still `PHI_FREE` (`hooks/phi-vet-gate.sh:31-33`), wiring it into `settings.json` *first* — while the Mac is still on the allowlist — is a safe no-op. Doing the `.local` removal first creates a real (if brief) window where the Mac reads `ASSUME_PHI` but has **zero** mechanical commit gate, because `phi-vet-gate.sh` isn't registered in `settings.json` yet — exactly the pre-existing gap the plan's own Background section says "matters more, not less, once the Mac drops off the PHI-free allowlist" (plan line 53). | The plan misses this because it treats "remove the allowlist line" and "wire the hook" as one atomic bullet pair rather than an ordered pair. | What to add: state the sub-order explicitly in Phase 2 — (1) wire `phi-vet-gate.sh` into `settings.json`, (2) confirm `is-phi-free-machine.sh --explain` still reports `PHI_FREE` (hook installed but inert — proves the wiring itself didn't break anything), (3) remove the `.local` allowlist line, (4) confirm it now reports `ASSUME_PHI`.

- **Scenario: `vm-shell-guard.sh` goes inert the moment Phase 2's allowlist edit lands, not when Phase 3 deletes it.** `vm-shell-guard.sh`'s machine gate is the *inverse* of `phi-vet-gate.sh`'s — it is active only when the machine reads `PHI_FREE` (`hooks/vm-shell-guard.sh:28-39`, `hooks/README.md:98`: "active on planner (PHI-FREE) machines... inert on the PHI VMs"). So Phase 2's allowlist removal alone silently disarms the SSH guard on the Mac, before Phase 3 ever runs. The plan's Phase 2 text does say this correctly ("this alone flips... vm-shell-guard.sh to inert"), but the Goal section's framing ("retire the hard boundary — not a soft downgrade") and a reader skimming only Phase 3 could come away thinking the guard stays live until its own deletion step. | Given the plan's explicit, Phil-confirmed intent is full retirement (not a staged downgrade), this ordering is actually *correct* — flag it as a documentation-clarity point, not a design flaw. | What to add: one sentence in Phase 2 making explicit that the SSH guard is already fully retired in practice the moment the allowlist edit lands, so Phase 3 is pure cleanup (deleting dead code + docs), not the moment the boundary actually goes away.

- **Scenario: a `git commit` lands on this very branch between Phase 1's `claude_ops.md` rewrite and Phase 2's hook wiring.** The plan's own Landing & cleanup section already catches this ("phi-vet itself is inert on this Mac until Phase 2 lands, so this branch's own commits still go through the *old* posture on the way in — expected, not a bug") — correct, and good that it's called out explicitly. No action needed here; noted because it's the one place the plan got this exact class of transition risk right.
